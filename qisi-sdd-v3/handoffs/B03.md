位置约定符合 `AGENTS.md:53`：「所有数据库 DDL 统一放在 `server/db/`，一张表对应一个 `<表名>.sql` 文件……不放入 `migrations/` 子目录」。新增 6 张 B 侧所需的表：

DDL 取自 `qisi-sdd-v3/contracts/database.sql`，唯一调整是**移除全部外键**。

**移除原因**：`AGENTS.md:53` 的命名规范（`<表名>.sql`）与 Kysely 的执行顺序互斥。Kysely 在 `node_modules/kysely/dist/migration/migrator.js:470-472` 做 `Object.keys(allMigrations).sort()`，按迁移名**字母序**执行；而字母序下 `node_runs`(n) 排在 `runs`(r) 之前，`node_runs → runs` 的外键必然建表失败。项目方选择合规命名，故移除外键。被移除的外键原文逐条保留在各自文件的头部注释中。

**代价，须知晓**：失去级联删除——删除 run 或 session 不再自动清理 `node_runs` / `events` / `probe_counters`。这与 `contracts/mysql.md` 的「FK级联是存储底线」相冲突，已上报项目方而非自行掩盖。**应用层必须自行承担清理**：删除/过期 run 时显式按 `run_id` 清理 `node_runs`；删除会话时显式清理 `events` 与 `probe_counters`。

**未验证声明**：项目方明确要求本次不执行 `db:migrate:dev`，因此**这批 DDL 未经真实 MySQL 执行**。它们是从规格包逐字派生并做了上述已知调整，但「照规格写」不等于「已跑通」。已知未验证项：语句在 MySQL 8.4.7 上的实际解析、`utf8mb4_0900_bin` 排序规则在建表时的接受度、`CHECK` 约束是否被实例真正强制。**在有人实际执行并回报之前，不得声称这 6 张表可用。**

## 查证结论：`model_calls` 与 `jobs` 两张表不建

`qisi-sdd-v3/contracts/workflow-persistence.md` §2 把 `model_calls`、`jobs` 与 requests/runs/events 并列为「事实」存储项，§3 也引用它们。但**规格的三处表清单一致地不收这两张表**：

- `contracts/database.sql`：19 张表，无 `model_calls`、无 `jobs`
- `contracts/mysql.md`：「schema_migrations + 原16业务表 + workflow_checkpoints/workflow_writes，共19张表」
- `contracts/README.md` §4 的表清单：同样未列

**归属**：`AGENTS.md` §4「B 定义工作流恢复需求，A 负责所有 MySQL 表迁移与数据库事务门面」；A01 步骤 4 原文「由A统一合入B提出的工作流 run/step/jobs 迁移」——**提出归 B、建表归 A**。

**且不需要建**，两条独立依据：

1. **`model_calls` 与契约直接冲突。** `domain.schema.json` 的 `RunRecord` 有 `calls` 字段，内嵌 `ModelCallRecord[]`（required，上限 20），落在 `runs.run_json`——DDL 已预留这条路径。更关键的是 `ModelCallRecord` 为 `additionalProperties: false` 且**不含 `provider_request_id`**，而 §2 要求该表存「provider request id」。独立建表装不下规格自己要求的字段，与契约直接冲突。另需注意 `runs.run_json` 内嵌上限 20 条，超限行为规格未定义，是唯一残留风险。
2. **`jobs` 可由 `runs` 行兼任。** `contracts/ports.ts` 中唯一的领取方法是 `claimRecovery(runId)`，形参是 **runId 而非 jobId**；`runs` 表已含 `lease_token UNIQUE`/`deadline_at`/`status`/`reserved_version`。规格 §3.2 只要求「`SELECT ... FOR UPDATE SKIP LOCKED` **或等价原子条件更新**」，§6 又允许「**等价**恢复协议」。

**建议**：按 19 表执行，并把 `workflow-persistence.md` §2/§3 的措辞改为指向 `runs`/`node_runs`；或反之补两张表并同步更新上述三处清单。**由项目方裁定，B 不自行择取**（`AGENTS.md` §1.2：规则冲突须报告并先解决，不能自行择取较宽松的一版）。

### 实测发现两个真实缺陷（此前无法发现，因为从未接过真实 provider）

**① 上游 400：`response_format: json_object` 要求 messages 含 "json"**

A 的适配器无条件设置 `response_format: {type:'json_object'}`，而 OpenAI 兼容网关要求 messages 中出现 "json" 字样，否则返回：

```
400 'messages' must contain the word 'json' in some form, to use 'response_format' of type 'json_object'
```

规格包的角色提示（`qisi-sdd-v3/prompts/*.md`）通篇不含 "json"——它们用中文写「仅返回目标Schema允许字段」。**两者直接组合会让每个角色、每次调用都 400。**

**② `outputSchema` 从未告知模型（这是 B01 自身的设计缺口）**

B 的 `ModelRequest.outputSchema` 只用于**事后校验**，从未下发给模型；而上游接口也不接收该字段。规格包的角色提示是中文散文，不含任何字段名。实测中模型据此自造字段：

```
实际返回 hypotheses[].gap_type / description / probe.question / expected_evidence
契约要求 hypotheses[].kind / explanation / missing_evidence / probe.goal_key / question_md / branches
```

结构校验必然失败，且修复重试也无效——重试只是把校验错误回注，模型仍不知道正确字段名。

**两者的修复都在桥接层**（`buildUpstreamSystem`）：把 `z.toJSONSchema(outputSchema)` 转成 draft 2020-12 注入 system，同时满足上面两条。不在提示词里补，是因为提示词与规格包逐字节一致是 B01 建立的保证、由 `prompts.spec.ts` 三方比对守住；这两条约束都是上游请求形态带来的，属桥接层职责。
